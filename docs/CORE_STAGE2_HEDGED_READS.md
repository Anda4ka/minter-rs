# Этап 2: hedged‑чтения RPC

Пояснительная записка ко второму этапу `docs/CORE_HARDENING_PLAN.md`. Цель —
убрать хвостовую задержку чтений, критичных у момента открытия минта (T0), не
меняя поведение при одном RPC‑узле.

---

## Background

### Совсем с нуля (можно пропустить)

Перед тем как «выстрелить» транзакцией минта, приложение делает несколько
**чтений** у ноды: текущий нонс кошелька (`eth_getTransactionCount`), время
последнего блока (`eth_getBlockByNumber`), иногда `chainId`. Если ведущая нода
подтормаживает (перегружена, плохой proxy), эти чтения добавляют задержку ровно
там, где каждая миллисекунда важна.

> **Hedged request (подстрахованный запрос).** Приём из распределённых систем:
> отправляем запрос на ноду 1; если она не ответила за небольшой порог —
> **параллельно** дублируем на ноду 2 (и 3), берём первый успешный ответ,
> остальные отменяем. Так «медленный хвост» одной ноды не тормозит всю операцию.
> Идея из статьи Dean & Barroso «The Tail at Scale».

### Узкий контекст

`RpcClient::call()` (`rpc.rs`) фейловерил ноды **последовательно** с таймаутом 5 с
на каждую: если ведущая нода зависла, мы ждали до 5 с прежде чем попробовать
следующую. При этом **отправка** транзакции уже шла параллельно на 3 ноды
(`send_raw_transaction`) — а вот чтения нет. Асимметрия ровно в горячем месте.

---

## Intuition

Добавляем «подстрахованное» чтение и пускаем через него только идемпотентные,
латентно‑чувствительные методы. Дублировать чтение безопасно — оно не меняет
состояние (в отличие от отправки tx, которую дублировать по этому пути нельзя).

Тайминг на игрушечных числах (порог `RPC_HEDGE_DELAY = 350 мс`):

```
t=0     → запрос на ноду A (ведущая)
t=350ms → A молчит → параллельно запрос на ноду B
t=360ms → B ответила → берём ответ B, задачу A отменяем
```

Против прежнего: если A висла, мы бы ждали её 5 c. Теперь возвращаемся за ~360 мс.
А если A ответила за 20 мс — B вообще не запускается (порог не достигнут), нагрузка
на ноды не растёт.

## Code

**Новый приватный метод `call_hedged`** (`rpc.rs`) на `tokio::task::JoinSet`:

```rust
const RPC_MAX_NODES: usize = 3;
const RPC_CALL_TIMEOUT: Duration = Duration::from_secs(5);
const RPC_HEDGE_DELAY: Duration = Duration::from_millis(350);

async fn call_hedged(&self, method, params) -> Result<Value> {
    // 1 URL → обычный таймированный вызов (поведение не меняется).
    // >1 URL: спавним ведущую; select! между «пришёл ответ» и «истёк порог».
    //   - ответ Ok → возвращаем, остальные задачи отменяются (drop JoinSet);
    //   - ответ Err и очередь пуста → сразу спавним следующую (быстрый failover);
    //   - истёк порог → параллельно спавним следующую.
}
```

Через него пущены только чтения у T0:

```rust
chain_id       → call_hedged("eth_chainId", …)
nonce          → call_hedged("eth_getTransactionCount", [addr, "pending"])
nonce_latest   → call_hedged("eth_getTransactionCount", [addr, "latest"])
block_timestamp→ call_hedged("eth_getBlockByNumber", ["latest", false])
```

Остальные методы (`balance`, `estimate_gas`, `eth_call`, `fee_history`, receipt,
отправка) остаются на прежних путях — блас‑радиус минимальный.

> **Почему не для отправки.** `call_hedged` рассылает запрос более чем одной ноде.
> Для `eth_sendRawTransaction` это делает специализированный
> `send_raw_transaction` (там дубли — фича). Для чтений дубли безопасны, для
> отправки логика уже своя.

## Verification

Тесты поднимают **настоящие** локальные mock‑сервера (raw HTTP/1.1 + JSON‑RPC) с
управляемой задержкой:

| Тест | Что проверяет | Итог |
|---|---|---|
| `hedged_uses_fast_node_when_lead_is_slow` | ведущая нода спит 1.5 c, вторая отвечает мгновенно → берём значение второй, `elapsed < 1200 мс` | ✅ |
| `hedged_single_url_returns_value` | один URL → путь без изменений | ✅ |
| `hedged_fast_error_fails_over_immediately` | быстрый JSON‑RPC error у ведущей → мгновенный переход на вторую | ✅ |

`cargo test -p minter-core` → **135 passed** (было 132, +3). Ручная проверка:
на RPC‑странице приложения задать быструю и медленную ноды и наблюдать, что
операции у T0 не «залипают» на медленной.

## Alternatives

**Всегда слать на все ноды параллельно (без порога).**

| За | Против (поэтому отклонено) |
|---|---|
| Минимальная задержка всегда | ×3 нагрузка/лимиты на здоровой ноде без нужды |
| Проще кода (нет таймера) | Приватные Alchemy‑ключи — лишний расход квоты |

**Динамический порог по истории латентности.**

| За | Против |
|---|---|
| Подстройка под сеть | Сложность, состояние, тонкая настройка |
| — | Для v1 хватает фиксированного 350 мс (вынесен в конст., этап 4 сделает конфигурируемым) |

## Quiz

<details>
<summary>1. Почему hedged‑путь применён к чтениям, но не к отправке tx?</summary>

- **A. (верно)** Чтения идемпотентны — дублировать безопасно; а `call_hedged`
  шлёт более чем одной ноде. Отправку дублирует свой `send_raw_transaction`, где
  это осознанная фича, а не побочный эффект чтения.
- **B.** Потому что отправка быстрее.
- **C.** Потому что tokio не умеет спавнить отправку.
</details>

<details>
<summary>2. Что произойдёт, если ведущая нода ответит за 20 мс?</summary>

- **A. (верно)** Вторая нода вообще не запустится — порог 350 мс не достигнут,
  лишней нагрузки нет.
- **B.** Всё равно запустятся все три ноды.
- **C.** Запрос завершится ошибкой.
</details>

<details>
<summary>3. Поведение при единственном RPC‑URL?</summary>

- **A.** Ошибка «нужно ≥2 ноды».
- **B. (верно)** Идентично прежнему: один таймированный вызов, никакого
  хеджирования.
- **C.** Дублируется на тот же URL дважды.
</details>

<details>
<summary>4. Как «медленная» задача отменяется после победы быстрой?</summary>

- **A. (верно)** Возврат из функции роняет `JoinSet`, что аварийно завершает
  оставшиеся задачи; их reqwest‑futures дропаются, соединения закрываются.
- **B.** Мы ждём её завершения, просто игнорируем результат.
- **C.** Она продолжает жить вечно.
</details>

<details>
<summary>5. Зачем в тесте mock‑сервер шлёт заголовок <code>connection: close</code>?</summary>

- **A.** Для скорости.
- **B. (верно)** Чтобы reqwest не держал keep‑alive на mock‑сокете и корректно
  завершал чтение ответа — тест детерминирован.
- **C.** Это требование JSON‑RPC.
</details>
