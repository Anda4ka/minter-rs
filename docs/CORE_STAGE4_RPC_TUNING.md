# Этап 4: константы и конфиг фанаута/таймаутов RPC

Пояснительная записка к четвёртому этапу `docs/CORE_HARDENING_PLAN.md`. Цель —
убрать «магические числа» из `rpc.rs` и дать возможность настраивать фанаут и
таймауты без правки кода, сохранив прежние дефолты.

---

## Background

### Совсем с нуля (можно пропустить)

`RpcClient` бьёт по нескольким нодам: сколько нод пробовать (**fan‑out**), сколько
ждать ответа (**timeout**) и, для «подстрахованных» чтений из этапа 2, через
сколько подключать следующую ноду (**hedge delay**). Разные сети ведут себя
по‑разному: быстрым L2 хочется таймаут пожёстче, медленному proxy — помягче.

### Узкий контекст

Числа были захардкожены и **повторялись** в нескольких методах: `.take(3)` в
`call`, `send_raw_transaction`, `transaction_receipt`; литерал
`Duration::from_secs(5)` в `call`. Дрейф между копиями — вопрос времени, а
поменять их под конкретную сеть можно было только пересборкой.

---

## Intuition

Один источник правды: маленькая структура `RpcTuning { max_nodes, call_timeout,
hedge_delay }` с дефолтами = прежним константам, читаемая из
env/настроек с **клампами** (чтобы кривой конфиг не отключил фанаут и не поставил
таймаут в 0). Клиент хранит `tuning` и использует его поля везде вместо литералов.

Игрушечный пример: оператор на быстром L2 ставит `RPC_CALL_TIMEOUT_MS=1500` —
чтения быстрее сдаются и переходят к следующей ноде. Ничего не задал — всё как
раньше (5000 мс, 3 ноды, 350 мс).

---

## Code

**Новая структура + разбор конфига** (`rpc.rs`):

```rust
pub struct RpcTuning { pub max_nodes: usize, pub call_timeout: Duration, pub hedge_delay: Duration }

impl RpcTuning {
    pub fn from_lookup<F: Fn(&str)->Option<String>>(get: F) -> Self {
        // RPC_MAX_NODES (1..=10), RPC_CALL_TIMEOUT_MS (500..=60000),
        // RPC_HEDGE_DELAY_MS (50..=5000); missing/garbage → default.
    }
}
```

`RpcClient` получает поле `tuning` (заполняется из env в конструкторе) и
использует `self.tuning.max_nodes` / `self.tuning.call_timeout` /
`self.tuning.hedge_delay` в `call`, `call_hedged`, `send_raw_transaction`,
`transaction_receipt`. Дефолты вынесены в именованные константы
`RPC_MAX_NODES` / `RPC_CALL_TIMEOUT` / `RPC_HEDGE_DELAY`.

Новые ключи задокументированы в `.env.example`.

> **Почему клампы, а не «как задал».** Конфиг — граница системы. `max_nodes=0`
> отключил бы фанаут, `timeout=0` мгновенно валил бы каждый вызов. Клампы
> превращают опасный ввод в безопасный диапазон.

## Verification

`cargo test -p minter-core` → **140 passed** (было 139, +1). Новый тест
`tuning_defaults_and_overrides` (чистый, без глобального env): дефолты =
константам; валидные оверрайды применяются; вне диапазона — клампятся; мусор →
дефолт. Прежние RPC‑тесты (hedged, receipt) зелёные — поведение по умолчанию не
изменилось.

Ручная проверка: запустить с `RPC_CALL_TIMEOUT_MS=1500` и убедиться, что медленная
нода сдаётся быстрее (в логах RPC).

## Alternatives

**Прокинуть настройки структурой через все вызовы вместо env.**

| За | Против (поэтому пока env/lookup) |
|---|---|
| Явные зависимости | Ripple через api/mint/raw/sweep, где строится `RpcClient` |
| — | `from_lookup` совместим с уже принятым в проекте env‑стилем (`GasParams::from_env`) |
| — | `from_lookup` тестируется без глобального состояния |

**Per‑chain таймауты.**

| За | Против |
|---|---|
| Точнее под сеть | Нужен реестр по chain_id; для v1 хватает глобальных + клампов |
