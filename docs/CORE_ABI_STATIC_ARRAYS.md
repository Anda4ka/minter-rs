# ABI: динамические массивы статических элементов (`T[]`)

Пояснительная записка к первому шагу пункта **#10** плана `IMPROVEMENT_PLAN.md`
(«Hot‑path tests + ABI completeness»). Добавлена поддержка кодирования
динамических массивов со статическими элементами: `uint256[]`, `address[]`,
`bytes32[]`, `bool[]`, `intN[]`, `bytesN[]`.

---

## Background

### Совсем с нуля (можно пропустить)

Чтобы вызвать функцию контракта, нужно собрать **calldata**: 4 байта селектора
(`keccak256("name(types)")[..4]`) + закодированные аргументы по правилам ABI.
Статические типы (`uint256`, `address`, `bool`, `bytesN`) занимают ровно одно
32‑байтовое слово. **Динамические** (`string`, `bytes`, массивы) кодируются в две
части: в «голове» лежит смещение (offset) до данных, а сами данные — в «хвосте».

> **Динамический массив `T[]`.** В хвосте: слово длины `n`, затем `n` элементов.
> Для статических элементов каждый элемент — одно 32‑байтовое слово. Пример:
> `bytes32[]` из двух хэшей → `[len=2][hash0][hash1]`.

### Узкий контекст

`abi.rs::build_calldata` умел статические типы + `string`/`bytes`, но на любой
массив или кортеж отвечал `"arrays/tuples not implemented"`. Из‑за этого нельзя
было вызвать частый паттерн клеймов — `claim(bytes32[] proof, …)` с merkle‑пруфом.

---

## Intuition

Массив статических элементов — это «длина + склейка обычных слов». Кодирование
одного элемента у нас уже есть (`encode_static_parameter`), значит массив — это
цикл поверх него плюс слово длины. Остаётся аккуратно вписать это в общий layout
head/tail (массив — динамический тип, в голову идёт offset).

Игрушечный пример: `airdrop(address[])` с `[0x1111…, 0x2222…]` →

```
селектор
голова:  offset = 0x20
хвост:   len = 2
         0x…1111  (address, выравнен вправо)
         0x…2222
```

Ввод оператора принимаем в трёх формах: `[a,b,c]`, `a,b,c`, одиночное значение.

## Code (`abi.rs`)

**Разбор типа и значений:**

```rust
pub fn parse_array_type(ty) -> Option<(String /*elem*/, Option<usize> /*T[n]?*/)>;
pub fn split_array_values(raw) -> Vec<String>;   // "[a,b]" | "a,b" | "a"
fn is_static_word_type(ty) -> bool;              // address/bool/uintN/intN/bytesN
```

**Кодирование массива (хвост):**

```rust
pub fn encode_static_array_dynamic(elem_ty, values) -> Result<Vec<u8>> {
    // [len] ++ concat(encode_static_parameter(elem_ty, v) for v in values)
}
```

**Интеграция:** `is_supported_type` теперь принимает `T[]` со статическим
элементом; `build_calldata`/`encode_parameter` в динамической ветке кодируют
массив. Точные сообщения об ошибках для ещё не поддержанных форм:

```rust
fn unsupported_type_error(ty) -> Error // "fixed-size arrays (…)", 
                                       // "dynamic-element arrays (…)", "tuples (…)"
```

> **Границы (осознанно вне этого PR):** фиксированные `T[n]` (Phase B),
> массивы динамических элементов `bytes[]`/`string[]` (Phase C) и кортежи
> `(…)` (Phase D). Они дают **понятную** ошибку, а не молча мис‑кодируются.
> Причина для B: `T[n]` статических элементов — это несколько слов в *голове*,
> а текущий `head_size = n_args * 32` этого не учитывает; отдельный аккуратный
> шаг.

## Verification

`cargo test -p minter-core` → **148 passed** (было 141, +7). Golden‑тесты
проверяют точный layout:

| Тест | Что проверяет |
|---|---|
| `encode_dynamic_address_array` | offset=0x20, len=2, два адреса |
| `encode_bytes32_array_merkle_proof` | пруф из двух `bytes32` |
| `encode_mixed_uint_then_array` | `claim(uint256,uint256[])`: offset=0x40, элементы 1,2,3 |
| `empty_array_encodes_length_zero` | `[]` → len 0 |
| `bracketed_and_bare_forms_are_equivalent` | `[1,2,3]` == `1,2,3` |
| `unsupported_array_and_tuple_forms_have_clear_errors` | `T[n]`/`bytes[]`/tuple → понятные ошибки |
| `parse_array_type_forms`, `split_array_values_forms` | разбор типов/значений |

Ручная проверка: на вкладке Raw Mint функция `claim(bytes32[])`, в параметрах —
`[0x…,0x…]`; Dry‑run покажет корректную calldata.

## Quiz

<details>
<summary>1. Почему массив — динамический тип, и что идёт в «голову»?</summary>

- **A. (верно)** В голову идёт **offset** до данных; сами `len`+элементы — в
  хвосте. Так ABI кодирует переменную длину.
- **B.** В голову идут все элементы подряд.
- **C.** Массивы кодируются как `bytes`.
</details>

<details>
<summary>2. Почему `uint256[3]` пока отклоняется, а `uint256[]` — нет?</summary>

- **A.** `[3]` синтаксически неверен.
- **B. (верно)** Фиксированный `T[n]` статических элементов занимает несколько
  слов в *голове*, а текущий `head_size = n_args*32` этого не учитывает — это
  отдельный шаг (Phase B). Динамический `T[]` укладывается в стандартный
  offset/tail.
- **C.** `[3]` — это кортеж.
</details>

<details>
<summary>3. Что вернёт кодировщик для `bytes[]`?</summary>

- **A.** Закодирует как `bytes`.
- **B. (верно)** Понятную ошибку «dynamic-element arrays (bytes[]) not yet
  supported» — элемент динамический (Phase C), молча не мис‑кодируем.
- **C.** Пустой массив.
</details>

<details>
<summary>4. Как оператор задаёт значения массива?</summary>

- **A. (верно)** Тремя формами: `[a,b,c]`, `a,b,c` или одиночное значение —
  `split_array_values` нормализует все.
- **B.** Только JSON.
- **C.** Через отдельные поля на каждый элемент.
</details>

<details>
<summary>5. Как переиспользован существующий код при кодировании элементов?</summary>

- **A. (верно)** Каждый элемент кодируется тем же `encode_static_parameter`, что
  и одиночные статические аргументы — массив это `len` + цикл поверх него.
- **B.** Через отдельный кодировщик, дублирующий логику.
- **C.** Через alloy.
</details>
