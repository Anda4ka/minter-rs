# Этап 3: детерминированная целочисленная математика газа

Пояснительная записка к третьему этапу `docs/CORE_HARDENING_PLAN.md`. Цель —
убрать `f64` из расчёта комиссий и лимита газа, чтобы значения были точными и
воспроизводимыми, сохранив прежние результаты на типовых входах.

---

## Background

### Совсем с нуля (можно пропустить)

Для EIP‑1559 транзакции задаются две величины: `maxFeePerGas` (потолок цены за
единицу газа) и `maxPriorityFeePerGas` (чаевые валидатору). Приложение считает
`maxFee` как `base_fee × множитель + priority`, где множитель — «запас» над
текущей базовой комиссией. Отдельно есть лимит газа = оценка × множитель.

> **Почему целые числа важны в деньгах.** `f64` хранит не все десятичные дроби
> точно и округляет по‑разному на границах. В блокчейне суммы — целые (wei), и
> расчёт должен быть детерминированным: одинаковый вход → одинаковый выход, без
> «плавающих» копеек.

### Узкий контекст

Было (в `gas.rs`):

```rust
// комиссия
base_fee * U256::from((params.base_fee_multiplier * 100.0) as u64) / U256::from(100)
// лимит газа
((base as f64) * mult).ceil() as u64
```

Проблема — не столько величины (для 1.15/2.0 всё точно), сколько **приведение
`множитель * 100.0 as u64`**: оно берёт целые проценты и **обрезает** дробь. Так
`1.155` превращался в `115` (×1.15), теряя 0.5%.

---

## Intuition

Переводим множитель в **базисные пункты** (bps, ×10 000) с явным округлением и
считаем в `U256`/целых. Bps дают точность до сотой процента, а `round()` вместо
обрезания делает приведение однозначным.

Игрушечный пример: `base_fee = 1 gwei`, множитель `1.155`.

```
Было:  (1.155 * 100) as u64 = 115  → base×115/100  = 1.150 gwei   (−0.5%)
Стало: round(1.155*10000)  = 11550 → base×11550/10000 = 1.155 gwei ✓
```

Для дефолтов ничего не меняется: `2.0 → 20000`, `1.15 → 11500` — те же числа.

---

## Code

**Новые целочисленные помощники** (`gas.rs`), рядом с уже существующим
`bump_fee_bps`:

```rust
pub fn multiplier_to_bps(m: f64) -> u64 {   // 2.0→20000, 1.155→11550; NaN/≤0 → 0
    if !m.is_finite() || m <= 0.0 { return 0; }
    (m * 10_000.0).round() as u64
}
pub fn mul_bps(value: U256, bps: u64) -> U256 { // value * bps / 10_000, saturating
    value.saturating_mul(U256::from(bps)) / U256::from(10_000)
}
```

**Комиссия** (обе ветки `Auto`/`Hybrid` в `calculate_fees`):

```rust
let mf = params.max_fee.unwrap_or_else(||
    mul_bps(base_fee, multiplier_to_bps(params.base_fee_multiplier)) + pf);
```

**Лимит газа** (`apply_gas_limit`): та же идея, целочисленно и без переполнения
(через `u128` + `div_ceil`):

```rust
let bps = if gas_multiplier > 1.0 { multiplier_to_bps(gas_multiplier) } else { 11_500 };
let mut limit = ((base as u128 * bps as u128).div_ceil(10_000)) as u64;
```

Публичные поля `GasParams` (`base_fee_multiplier: f64`, `gas_multiplier: f64`)
намеренно **не тронуты** — чтобы не тащить изменения через все вызывающие места,
UI и сериализацию; перевод в целые происходит в одной точке расчёта.

## Alternatives

**Сделать поля `GasParams` целыми (bps) вместо `f64`.**

| За | Против (поэтому отклонено сейчас) |
|---|---|
| Ни одного `f64` в типе | Ripple через api/mint/raw/disperse/UI + сериализация |
| Тип честнее | Большой дифф, риск на многих вызывающих |
| — | Перевод в одной точке даёт 95% пользы без этого риска |

**Оставить `f64`‑математику.**

| За | Против |
|---|---|
| Ноль изменений | Обрезание дроби множителя; недетерминированные границы |

## Quiz

<details>
<summary>1. Почему bps, а не целые проценты?</summary>

- **A. (верно)** Проценты (`×100`) теряют сотые процента при обрезании (1.155→115);
  bps (`×10 000`) их сохраняют.
- **B.** bps быстрее считаются.
- **C.** Того требует EIP‑1559.
</details>

<details>
<summary>2. Изменится ли результат для дефолтного множителя 2.0?</summary>

- **A. (верно)** Нет: `2.0 → 20000`, `base×20000/10000 = base×2` — идентично старому
  `base×200/100`.
- **B.** Да, станет ×2.0001.
- **C.** Да, округлится вниз.
</details>

<details>
<summary>3. Почему в <code>apply_gas_limit</code> используется <code>u128</code>?</summary>

- **A.** Для точности дробей.
- **B. (верно)** Чтобы `base * bps` не переполнилось до деления (`u128` с запасом),
  затем `div_ceil` и обратно в `u64`.
- **C.** Требование alloy.
</details>

<details>
<summary>4. Что вернёт <code>multiplier_to_bps(f64::NAN)</code> и почему это важно?</summary>

- **A. (верно)** `0` — защита от «мусорного» множителя из настроек; функция
  проверяет `is_finite()` и `≤ 0`.
- **B.** Паникует.
- **C.** `u64::MAX`.
</details>

<details>
<summary>5. Почему поля <code>GasParams</code> оставлены <code>f64</code>?</summary>

- **A.** Так требует serde.
- **B. (верно)** Чтобы не тащить изменение типа через множество вызывающих, UI и
  сериализацию; перевод в целые сделан в одной точке расчёта — минимальный риск.
- **C.** `f64` точнее целых.
</details>
