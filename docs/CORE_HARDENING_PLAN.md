# План: упрочнение логики ядра (`minter-core`)

Живой план работ по «пробелам логики», найденным в код‑ревью ядра. Идём
**поэтапно**: каждый этап — отдельный PR с тестами и пояснительной запиской.

## Принципы

- **Горячий путь минта трогаем осторожно.** Инструмент двигает реальные средства;
  где поведение менять не нужно — сохраняем его 1:1 (рефактор без смены семантики),
  а где меняем — покрываем тестами и объясняем в записке.
- **Один этап — один PR.** Маленькие, проверяемые диффы; легко ревьюить и откатывать.
- **Тесты вперёд поведения.** Чистые функции тестируем таблично, без сети.
- Без оценок сроков — только объём и порядок.

## Этап 1 — Единая таксономия RPC/tx‑ошибок

**Проблема.** Классификация ошибок разбросана и матчится по подстрокам:
`classify_mint_error`, `is_already_known`, `is_nonce_too_low`, `is_underpriced`
(`mint.rs:87–133`), `is_intrinsic_gas_error` (`gas.rs:143`). Провайдеры
(Geth/Erigon/Nethermind/Alchemy/publicnode) формулируют по‑разному, часть отдаёт
структурный код JSON‑RPC. Неверная классификация в бою = пропущенный RBF или
ложный «insufficient funds».

**Подход.**
- Новый модуль `errors.rs`: enum `TxErrorKind` + `classify(msg) -> TxErrorKind` и
  тонкие предикаты. Матч по коду JSON‑RPC (если есть в строке) + курируемый список
  фраз (надмножество текущих, только однозначные синонимы).
- Существующие функции в `mint.rs`/`gas.rs` делегируют в модуль — сигнатуры и
  вывод сохраняются (поведение прежнее, набор распознаваемых строк шире).
- Табличные тесты с реальными формулировками провайдеров.

**Готово, когда:** все прежние тесты зелёные + новые табличные; поведение на
известных входах не изменилось; классификаторы вызываются из одного места.

## Этап 2 — Hedged‑чтения RPC

**Проблема.** `RpcClient::call()` (`rpc.rs:287`) фейловерит ноды последовательно
(таймаут 5s каждая → до ~15s). Отправка tx уже параллельна (`send_raw_transaction`),
а чтения — нет. У снайпера перед T0 идёт refresh нонсов/таймстампа — медленная
ведущая нода добавляет хвост.

**Подход.** Добавить «hedged» чтение: старт на ноде 1; если нет ответа за порог
(~300–500 мс) — параллельно дублируем на 2/3, берём первый успех. Применяем к
латентно‑чувствительным чтениям (`nonce`, `block_timestamp`, `chain_id`).
Для одной ноды поведение неизменно. Порог — константа/конфиг (стык с этапом 4).

**Готово, когда:** одно‑нодовый путь без изменений; для нескольких нод p99 чтения
падает; есть тест на «первый успех выигрывает / медленная нода не блокирует».

## Этап 3 — Детерминированная целочисленная математика газа

**Проблема.** `gas.rs` использует float: `base_fee_multiplier * 100.0 as u64`
(`:28,:39`) и `((base as f64) * mult).ceil() as u64` (`:85`). Float даёт
неустойчивое округление на границах; комиссии должны быть воспроизводимыми.

**Подход.** Множители — целые (bps/ppm), вся арифметика в `U256`/целых. Сохранить
внешние дефолты (1.15 → 11500 bps и т.п.). Тесты на округление и границы.

**Готово, когда:** значения совпадают со старыми на типовых входах, детерминированы
на границах; тесты покрывают floor/cap/множитель.

## Этап 4 — Константы и конфиг фанаута/таймаутов RPC

**Проблема.** `take(3)` и `Duration::from_secs(5)` захардкожены в нескольких
методах `rpc.rs` → дрейф значений; быстрым L2 нужен таймаут жёстче.

**Подход.** Вынести в именованные константы; дать необязательный override из
настроек (per‑chain по возможности). Дефолты как сейчас.

**Готово, когда:** магические числа устранены; дефолтное поведение неизменно;
override читается из настроек.

---

## Этап 5 — Наблюдаемость отправки tx

**Проблема.** `send_raw_transaction` возвращает первый успешный хэш, но не
сообщает, какая нода выиграла и что ответили остальные.

**Подход.** Вернуть структуру с per‑node исходом; прокинуть в reporter/лог. Стык с
планом #9 (метрики фаз sign/send/receipt).

**Готово, когда:** видно ноду‑победителя и ошибки остальных; хэш‑контракт метода
для вызывающих сохранён.
