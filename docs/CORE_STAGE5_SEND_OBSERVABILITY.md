# Этап 5: наблюдаемость отправки транзакции

Пояснительная записка к пятому (финальному) этапу `docs/CORE_HARDENING_PLAN.md`.
Цель — видеть, **какая нода** приняла бродкаст и что ответили остальные, не меняя
контракт возвращаемого хэша для вызывающих.

---

## Background

### Совсем с нуля (можно пропустить)

Когда транзакция готова, её «бродкастят» — рассылают на несколько RPC‑нод сразу,
чтобы хоть одна быстро приняла в мемпул. `send_raw_transaction` шлёт на все ноды
параллельно и возвращает первый принятый хэш; остальные задачи отменяются.

### Узкий контекст

Функция возвращала только `B256` (хэш). Наружу не выходило, **кто** выиграл и
почему проиграли другие — это мешает диагностике («почему бродкаст медленный?»,
«эта нода стабильно отклоняет?») и не даёт данных для будущих метрик фаз
(sign/send/receipt — план #9). Внутри уже были `rlog!`, но без структуры.

---

## Intuition

Разделяем «что вернуть вызывающему» и «что зафиксировать для наблюдения». Вводим
`SendReport { hash, winner, nodes_tried, losers }`. Публичный
`send_raw_transaction` остаётся `-> Result<B256>` (делегирует и берёт `.hash`), а
новый `send_raw_transaction_report` отдаёт полную картину.

Игрушечный пример: ноды `[A, B]`, A отклонила (`-32000 nope`), B приняла →

```
SendReport { hash: 0x…, winner: "B", nodes_tried: 2, losers: ["A: … nope"] }
лог: RPC send OK via B (after 1 failed: A: … nope)
```

> **Честность отчёта.** Мы ждём ответы в порядке нод и по первому Ok возвращаемся,
> отменяя остальные. Поэтому `losers` — это ноды, которые **ошиблись до
> победителя**; про отменённые (после победителя) мы честно ничего не пишем.

## Code

**Новая структура** (`rpc.rs`):

```rust
pub struct SendReport {
    pub hash: B256,        // принятый хэш
    pub winner: String,    // короткий URL ноды-победителя
    pub nodes_tried: usize,
    pub losers: Vec<String>, // "shorturl: error" тех, кто ошибся до победителя
}
```

**Рефактор без смены контракта:**

```rust
pub async fn send_raw_transaction(&self, raw) -> Result<B256> {
    self.send_raw_transaction_report(raw).await.map(|r| r.hash)
}
pub async fn send_raw_transaction_report(&self, raw) -> Result<SendReport> {
    // тот же параллельный бродкаст; копим losers; на первом Ok — отменяем
    // остальных и возвращаем SendReport; лог теперь с winner + losers.
}
```

Логика гонки/отмены/фанаута (через `self.tuning.max_nodes` из этапа 4) не
изменилась — только добавлены сбор `losers` и обогащённый лог.

## Alternatives

**Сменить возвращаемый тип `send_raw_transaction` на `SendReport`.**

| За | Против (поэтому обёртка) |
|---|---|
| Один метод | Ripple через всех вызывающих в mint/raw/sweep |
| — | Обёртка `-> B256` сохраняет совместимость; отчёт берут те, кому он нужен |

  `send_raw_transaction_report` и берёт `.hash`. Полный отчёт — по желанию.
- **B.** Потому что `SendReport` не `Send`.
- **C.** Из-за alloy.

<details>
<summary>2. Кто попадает в `losers`?</summary>

- **A.** Все ноды, кроме первой.
- **B. (верно)** Только те, что **ошиблись до победителя**; ноды, отменённые
  после победы, не фиксируются (мы не знаем их исход).

</details>

  добавлены только сбор `losers` и обогащённый лог. Фанаут берётся из
  `self.tuning.max_nodes` (этап 4).

</details>
